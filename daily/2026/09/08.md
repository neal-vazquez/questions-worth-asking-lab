# Constraint-first product variant generation

**Date:** 2026-09-08  
**Area:** Data modeling / digital product systems  
**Status:** Conceptual pattern with synthetic examples

## Question

How should a product system generate many variants while preventing combinations that are technically possible but visually invalid?

## Model valid combinations, not every combination

A naive catalog creates the Cartesian product:

```text
design × asset treatment × product color × size × print scale
```

That approach treats every combination as valid until rules remove the bad ones. As the catalog grows, exclusions become difficult to reason about and easy to miss.

A safer approach defines an eligibility predicate first:

```text
eligible(design, treatment, color, size, scale) -> true | false
```

Only eligible tuples become variants.

## Synthetic contrast example

Assume two asset treatments:

- `dark-lines`, intended for light backgrounds
- `light-lines`, intended for dark backgrounds

And four synthetic garment colors:

| Color | Tone class | Eligible treatment |
|---|---|---|
| cloud | light | dark-lines |
| sand | light | dark-lines |
| navy | dark | light-lines |
| charcoal | dark | light-lines |

The core rule is:

```python
def treatment_for(tone_class: str) -> str:
    return {
        "light": "dark-lines",
        "dark": "light-lines",
    }[tone_class]
```

This is an allowlist. An unknown tone class fails closed instead of silently receiving an arbitrary treatment.

## Separate independent and dependent dimensions

Some dimensions may be independent:

- size
- print scale
- product cut

Others are dependent:

- asset treatment depends on background tone
- print area may depend on product type
- available scale may depend on printable dimensions

Representing those dependencies explicitly prevents a flat spreadsheet from disguising business rules as duplicated rows.

## Validation invariants

Before publishing generated variants, assert that:

1. every active color has exactly one tone class;
2. every tone class maps to an approved treatment;
3. no variant combines low-contrast treatment and background;
4. variant identifiers are unique;
5. prices and availability are defined for every published tuple;
6. generated image references exist;
7. zero unpublished source assets appear in the output.

## Why this matters

Variant count is not a quality metric. A smaller, valid catalog is more useful than a large catalog containing combinations that should never reach a customer.

Constraint-first generation also makes changes safer. Adding a new color requires classifying its tone once. The generator and tests then apply the same rule across every eligible size and scale, reducing manual inconsistency without pretending aesthetic judgment has been automated away.
