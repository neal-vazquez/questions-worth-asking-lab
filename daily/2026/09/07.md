# Transparency without exposure

**Date:** 2026-09-07  
**Area:** Responsible AI / philosophy of technology  
**Status:** Working principle, not an empirical result

## Question

How can an AI-assisted project remain transparent when its source material, implementation details, or working drafts should stay private?

## Core distinction

Transparency is not the same as maximal disclosure.

A system can expose every artifact and still be difficult to evaluate. It can also protect sensitive inputs while making its method, boundaries, and accountability structure clear. The relevant goal is **inspectability**: give observers enough information to understand what the system does, who is responsible, how claims are checked, and what remains outside public scope.

## Three-layer model

| Layer | Public purpose | Appropriate contents |
|---|---|---|
| Method | Explain how work is produced | workflow, evaluation rules, schemas, synthetic examples |
| Evidence | Support specific public claims | citations, reproducible public data, non-sensitive validation records |
| Protected work | Preserve necessary confidentiality | raw exports, unpublished drafts, credentials, private source material |

The public layer should describe the boundary rather than pretending the protected layer does not exist.

## Minimum viable transparency

A public project should answer five questions:

1. What role did AI play?
2. What role did the human operator play?
3. Which claims are directly supported, inferred, or still provisional?
4. What validation occurred before publication?
5. What categories of material are intentionally withheld, and why?

These answers create accountability without requiring disclosure of the protected material itself.

## Boundary rule

Before moving an artifact from private work into a public repository, classify it:

```text
PUBLIC
  Safe and useful as written.

DERIVED
  Publish only after removing protected inputs and preserving the general method.

POINTER
  State that a private source exists, without exposing its contents or identifiers.

PRIVATE
  Do not publish, quote, summarize, or place in public history.
```

A branch or pull request in a public repository counts as publication. Deleting a secret later does not erase it from repository history.

## Practical test

A release is appropriately transparent when a reviewer can evaluate the public claim and workflow without needing access to information that has no legitimate reason to be public.

That standard rejects two bad shortcuts:

- secrecy presented as rigor;
- exposure presented as honesty.

Responsible transparency reveals the structure of accountability while preserving the boundaries that accountability requires.
